`AssetCache.preload` previously awaited each asset's complete read, fetch, hash and persistent transaction before starting the next. The candidate overlaps at most four loads while reserving no more than the largest input asset's declared bytes. It keeps every asset, the existing content-addressed cache, ordinary load/coalescing behavior and input-order progress after each durable commit. It retains no successful response body in its job outcomes.

If an input load or progress callback fails, already dispatched jobs settle before rejection. Successful suffix jobs may therefore be cached, unlike the original sequential implementation. The earliest failing input's thrown object is preserved, no later window starts, and retries use the existing cache normally. These changed suffix side effects and failure timing are deliberate and covered by tests. The byte reservation uses declared sizes; it does not bound corrupt cached bodies, ignored-Range full responses or all browser/native memory.

One sequential original→candidate experiment used fresh headed Chromium profiles, the actual frozen `dataset.preloadGeographicSources` function, real IndexedDB transactions and all city-source assets. It imported no game boot, scene, atlas, map preparation or workers. Both variants had the same common I/O observer and immutable body pool; only `AssetCache.ts` differed.
